# Writing Data

All write operations must run inside an `aggo.tx { }` block. The block runs
inside a `BEGIN … COMMIT` transaction. Any exception triggers automatic rollback.

## INSERT

### Insert an entity

The most common form: pass the entire entity. Columns marked `isGenerated = true`
are skipped automatically (the database fills those in).

```kotlin
val user = User(
    id        = UserId(Tsid.generate().value),
    email     = Email("alice@example.com"),
    name      = "Alice",
    active    = true,
    createdAt = Instant.now(),  // isGenerated=true, skipped in INSERT
)

aggo.tx { insert(UsersTable, user) }
```

### Insert with a builder block

Use the builder form when the full entity is not available, or when you want to
set only specific columns:

```kotlin
aggo.tx {
    insert(UsersTable) {
        UsersTable.email  setTo Email("alice@example.com")
        UsersTable.name   setTo "Alice"
        UsersTable.active setTo true
        // created_at is isGenerated=true — omit it, DB provides the value
    }
}
```

### Insert and get the generated primary key

Use `insertReturning` when the primary key is generated by the database (e.g.
a SERIAL column or `DEFAULT gen_random_uuid()`):

```kotlin
val newId: UUID? = aggo.tx {
    insertReturning(UsersTable, UsersTable.id) {
        UsersTable.email  setTo Email("alice@example.com")
        UsersTable.name   setTo "Alice"
        UsersTable.active setTo true
    }
}
// newId is the UUID generated by the database
```

Works with any PK type — `UUID`, `Long`, `String` (TSID/ULID), `Int`, etc.

## UPDATE

```kotlin
val affected: Long = aggo.tx {
    update(UsersTable) {
        UsersTable.active setTo false
        UsersTable.name   setTo "Deactivated User"
        where { UsersTable.id eq userId }
    }
}
check(affected == 1L) { "user $userId not found" }
```

Omitting `where` updates every row in the table.

Multiple columns can be updated in one statement:

```kotlin
aggo.tx {
    update(UsersTable) {
        UsersTable.name      setTo newName
        UsersTable.email     setTo newEmail
        UsersTable.updatedAt setTo Instant.now()
        where { UsersTable.id eq userId }
    }
}
```

## DELETE

```kotlin
// Delete by primary key
aggo.tx { delete(UsersTable) { where { UsersTable.id eq userId } } }

// Delete with a compound WHERE
aggo.tx {
    delete(UsersTable) {
        where { (UsersTable.active eq false) and UsersTable.deletedAt.isNotNull() }
    }
}

// Delete all rows (no WHERE — be careful!)
aggo.tx { delete(UsersTable) }
```

## Transactions — multi-statement atomicity

All statements inside a single `aggo.tx { }` block share one connection and one
transaction. Either all statements commit, or all roll back together.

```kotlin
aggo.tx {
    // Both inserts succeed or both roll back
    insert(OrdersTable, order)
    insert(OrderLinesTable, line)
}
```

### Conditional logic inside a transaction

```kotlin
aggo.tx {
    val affected = update(OrdersTable) {
        OrdersTable.status setTo "PROCESSING"
        where { (OrdersTable.id eq orderId) and (OrdersTable.status eq "PENDING") }
    }
    // If nobody else changed the order first, record the event
    if (affected > 0) {
        insert(EventsTable) {
            EventsTable.orderId setTo orderId
            EventsTable.type    setTo "ORDER_PROCESSING_STARTED"
        }
    }
}
```

### Returning values from a transaction

```kotlin
val result = aggo.tx {
    val id = insertReturning(InvoicesTable, InvoicesTable.id) {
        InvoicesTable.orderId setTo orderId
        InvoicesTable.amount  setTo total
    }
    update(OrdersTable) {
        OrdersTable.invoiceId setTo id
        where { OrdersTable.id eq orderId }
    }
    id   // the return value of aggo.tx is the last expression
}
```

### Error handling

Any exception thrown inside `aggo.tx { }` — including custom business exceptions —
triggers a rollback. The caller always catches the original exception type:

```kotlin
try {
    aggo.tx {
        insert(UsersTable, user)
        check(quota > 0) { "quota exceeded" }  // throws IllegalStateException
    }
} catch (e: IllegalStateException) {
    // transaction was rolled back; e.message == "quota exceeded"
}
```

## transaction — typed transaction results

Use `aggo.transaction { ... }` when callers should receive a typed result
instead of catching exceptions. The return type is
`Transaction<Success, Error>`, which has the same composition helpers as
`Query`.

```kotlin
val result: Transaction<Long, AggoError> = aggo.transaction {
    insert(UsersTable, user)
}

result.fold(
    onSuccess = { rows -> println("inserted $rows row") },
    onFailure = { error -> println("write failed: $error") },
)
```

The transaction still rolls back on failure. The difference is only the caller
contract: errors are returned as `Query.Failure(...)` instead of being
thrown through your application layer.

### Mapping constraint errors

Build a `ConstraintErrorMap` from the tables involved in the transaction and
pass it to `transaction`.

```kotlin
val errorMap = constraintErrorMap(UsersTable, ProfilesTable)

val result = aggo.transaction(errorMap) {
    val rows = insert(UsersTable, user)
    insert(ProfilesTable, profile)
    rows
}
```

If the database reports a known check, unique, or foreign-key violation, Aggo
returns `ConstraintError` with a stable application key:

```kotlin
result.fold(
    onSuccess = { rows -> Created(rows) },
    onFailure = { error ->
        when (error) {
            is ConstraintError -> BadRequest(
                field = error.column,
                code = error.key,
            )
            is DatabaseError -> InternalServerError("database.error")
            else -> InternalServerError("unknown.error")
        }
    },
)
```

Typical keys come from schema declarations:

```kotlin
val email = varchar("email", 255)
    .required()
    .unique(key = "user.email.taken")
    .check(Checks.email(), key = "user.email.invalid") { it.email }

val workspaceId = varchar("workspace_id", 26)
    .required()
    .references(Workspaces.id, key = "workspace.missing") { it.workspaceId }
```

This keeps API error mapping independent from SQL text and database exception
classes.

### One-shot helpers on Aggo

For simple single-statement writes, you can skip the `tx { }` block entirely:

```kotlin
// These are exactly equivalent to aggo.tx { insert(…) }, aggo.tx { update(…) }, etc.
aggo.insert(UsersTable, user)
aggo.update(UsersTable) { UsersTable.active setTo false; where { UsersTable.id eq id } }
aggo.delete(UsersTable) { where { UsersTable.id eq id } }
```
